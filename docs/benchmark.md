# 벤치마크

> Phase 2 측정 기록. 삽입 성능 (S28) 은 아래에 있고, 인덱스 대 선형 탐색 비교는 S29 에서 이어서 채운다.

| 항목 | 값 |
|---|---|
| CPU | Intel Core i5-8257U @ 1.40GHz (호스트), 컨테이너에 2 코어 할당 |
| 메모리 | 컨테이너 3.9 GB |
| OS | Docker Desktop (linuxkit 커널 7.0.12) 안의 Linux 컨테이너 |

| 데이터 경로 | 컨테이너 내부 `/tmp` (bind mount 경로가 아님: 호스트 파일 공유 비용이 섞이지 않게) |

## 삽입 성능 (S28)

### 방법

```bash
mkdir -p /tmp/mdb-bulk/data
./minidb -d /tmp/mdb-bulk/data init schema/users.sql
python3 tools/gen_sql.py 1000000 > /tmp/mdb-bulk/bulk.sql   # 44.8 MB
./minidb -d /tmp/mdb-bulk/data -q /tmp/mdb-bulk/bulk.sql
```

SQL 경로 전체 (읽기 → 토크나이저 → 파서 → 검증 → 실행 → 인덱스 등록) 를 거친다. `-q` 라서 결과 출력 비용은 없다.
시간과 최대 메모리는 Python `subprocess` + `resource.getrusage(RUSAGE_CHILDREN)` 으로 쟀다.

### 결과 (100 만 건)

| 항목 | 값 |
|---|---|
| SQL 생성 (`gen_sql.py`) | 2.4 s |
| 실행 시간 | 3.25 s |
| 초당 건수 | 약 31 만 건/s |
| 결과 | `1000000 statements, 0 errors`, `users.tbl` 40,001,024 B (= 1024 + 100 만 × 40) |
| 최대 메모리 (RSS) | 67.8 MB (스크립트 전체 44.8 MB + 인덱스 + 결과) |

### 병목: 헤더 갱신 `pwrite`

INSERT 한 건은 레코드 `pwrite` (40 B) 와 헤더 카운터 `pwrite` (8 B) 를 한 번씩 한다. 두 쓰기만 따로 100 만 번씩 실행해 비용을 쟀다 (같은 환경, 같은 파일 크기).

| 시스템 콜 | 100 만 번 | 전체 3.25 s 대비 |
|---|---|---|
| 레코드 `pwrite` | 0.94 s | 약 29 % |
| 헤더 `pwrite` | 0.81 s | 약 25 % |
| 나머지 (파싱·검증·인코딩·트리 삽입) | 약 1.5 s | 약 46 % |

**결정: 헤더 갱신을 묶지 않는다.** 묶으면 최대 25 % 정도 빨라지지만,

- 100 만 건이 3 초대라 목표 (100 만 건 이상 넣고 측정) 에 이미 충분하다.
- 묶으면 스크립트 도중 종료 시 헤더가 크게 뒤처지고, 일관성을 S25 의 복구 (꼬리 레코드 채택) 에 전적으로 의존하게 된다. 지금은 문장마다 헤더가 맞아서 복구는 "레코드와 헤더 사이" 의 아주 짧은 구간만 다룬다.
- Phase 3 서버에서는 요청마다 INSERT 가 하나라 묶을 단위가 없다.

### 강제 종료 (E28-04)

100 만 건 실행 도중 파일이 12 MB 를 넘었을 때 `kill -9` 로 죽였다 (종료 상태 137).

- 파일의 완전한 레코드 300,131 개, 헤더 `row_count = 300131`, `next_id = 300132` 로 일관됨 (문장 경계에서 죽음)
- 다시 열고 INSERT 하면 id 300132 부터 이어짐
- 레코드는 썼는데 헤더 갱신 전에 죽는 경우는 구간이 짧아 수동으로 맞히기 어렵다. 그 상태는 `test_index.c` 의 E25-01 이 헤더를 직접 되돌려 재현하고, 열 때 복구됨을 검사한다.
