# 벤치마크

> Phase 2 측정 기록: id B+ 트리 인덱스 경로와 선형 탐색을 비교하고 (S29), 대량 삽입 성능을 잰다 (S28).
> Phase 3 측정 기록: HTTP API 서버에 `wrk` 로 부하를 걸어 워커 수별, 락 방식별 처리량을 잰다 (S44).

## 요약

- 100 만 건에서 `WHERE id = k` (인덱스) 는 **약 2 µs**, `WHERE name = 'userk'` (선형) 는 **약 34 ms** — 약 **15,000 배** 차이.
- 인덱스 검색은 N 이 1 만 → 100 만 (100 배) 이 되어도 거의 일정하고, 선형 탐색은 N 에 정비례해서 10 배씩 늘어난다.
- 트리 높이는 1 만·10 만 건에서 3, 100 만 건에서 4 (`BTREE_ORDER` 128). 100 만 건 재구축은 약 140 ms.
- 100 만 건 INSERT 는 SQL 경로 전체를 거쳐 약 3.3 s (초당 약 30 만 건).
- (Phase 3) HTTP 서버는 id 조회 90% 부하에서 워커 수·락 방식과 관계없이 **초당 약 1.5 만 ~ 1.9 만 요청**. 병목은 락이 아니라 요청마다 TCP 연결을 맺고 끊는 비용과, `wrk` 와 서버가 코어 2 개를 나눠 쓰는 것이다.
- (Phase 3) 락 안에 오래 머무는 선형 스캔 읽기에서는 `TABLE_RW` 가 `GLOBAL` 의 **약 1.9 배** (477 대 251 req/s). 코어 2 개에서 기대할 수 있는 최대치에 가깝다.

## 삽입 성능 (S28)

### 방법

```bash
mkdir -p /tmp/mdb-bulk/data
./minidb -d /tmp/mdb-bulk/data init schema/users.sql
python3 tools/gen_sql.py 1000000 > /tmp/mdb-bulk/bulk.sql   # 44.8 MB
./minidb -d /tmp/mdb-bulk/data -q /tmp/mdb-bulk/bulk.sql
```

SQL 경로 전체 (읽기 → 토크나이저 → 파서 → 검증 → 실행 → 인덱스 등록) 를 거친다. `-q` 라서 결과 출력 비용은 없다.
시간과 최대 메모리는 Python `subprocess` + `resource.getrusage(RUSAGE_CHILDREN)` 으로 쟀다.

### 결과 (100 만 건)

| 항목 | 값 |
|---|---|
| SQL 생성 (`gen_sql.py`) | 2.4 s |
| 실행 시간 | 3.25 s |
| 초당 건수 | 약 31 만 건/s |
| 결과 | `1000000 statements, 0 errors`, `users.tbl` 40,001,024 B (= 1024 + 100 만 × 40) |
| 최대 메모리 (RSS) | 67.8 MB (스크립트 전체 44.8 MB + 인덱스 + 결과) |

### 병목: 헤더 갱신 `pwrite`

INSERT 한 건은 레코드 `pwrite` (40 B) 와 헤더 카운터 `pwrite` (8 B) 를 한 번씩 한다. 두 쓰기만 따로 100 만 번씩 실행해 비용을 쟀다 (같은 환경, 같은 파일 크기).

| 시스템 콜 | 100 만 번 | 전체 3.25 s 대비 |
|---|---|---|
| 레코드 `pwrite` | 0.94 s | 약 29 % |
| 헤더 `pwrite` | 0.81 s | 약 25 % |
| 나머지 (파싱·검증·인코딩·트리 삽입) | 약 1.5 s | 약 46 % |

### 구간별 타이머 (INSERT 경로 전체)

위 표는 시스템 콜만 따로 잰 것이라 나머지를 한 덩어리로 봤다. 정확히 나누려고 소스 사본 (커밋하지 않음) 에 `clock_gettime` 타이머를 넣어
`./minidb -q bulk.sql` 100 만 건을 같은 환경에서 세 번 돌렸다. 세 번이 거의 같아서 가운데 값을 적는다.

| 구간 | 100 만 건 | INSERT 1 건당 | 비중 |
|---|---|---|---|
| 레코드 `pwrite` (40 B) | 1,104 ms | 1.10 µs | 29 % |
| 헤더 `pwrite` (8 B) | 965 ms | 0.97 µs | 26 % |
| SQL 파싱 (토크나이저 + 파서) | 807 ms | 0.81 µs | 21 % |
| `btree_insert` | 214 ms | 0.21 µs | 6 % |
| 결과 전달 + `statement_free` | 100 ms | 0.10 µs | 3 % |
| 검증 (`validator_check`) | 73 ms | 0.07 µs | 2 % |
| 레코드 인코딩 (+ 버퍼 `malloc`/`free`) | 72 ms | 0.07 µs | 2 % |
| 파일 읽기 (44.8 MB) | 11 ms | — | 0.3 % |
| 그 밖 (타이머 비용 포함) | 407 ms | 0.41 µs | 11 % |
| **합계** | **3,753 ms** | 3.75 µs | |

- 타이머 한 번이 약 24 ns 이고 문장마다 18 번 불러서 약 0.45 s 가 더해졌다 (타이머 없는 빌드는 같은 시점에 3.26 s). "그 밖" 의 대부분이 이 비용이다.
- **시스템 콜 두 개가 55 %**, 파싱이 21 %, B+ 트리 삽입은 6 % 다. 트리는 병목이 아니다.
- 트리 삽입 0.21 µs 는 재구축 (100 만 건 140 ms, 읽기 포함) 의 건당 시간보다 크다. 재구축은 삽입만 연달아 해서 노드가 CPU 캐시에 남지만, SQL 경로에서는 삽입 사이에 파싱·시스템 콜이 끼어 캐시가 식기 때문이다.

**결정: 헤더 갱신을 묶지 않는다.** 묶으면 최대 25 % 정도 빨라지지만,

- 100 만 건이 3 초대라 목표 (100 만 건 이상 넣고 측정) 에 이미 충분하다.
- 묶으면 스크립트 도중 종료 시 헤더가 크게 뒤처지고, 일관성을 S25 의 복구 (꼬리 레코드 채택) 에 전적으로 의존하게 된다. 지금은 문장마다 헤더가 맞아서 복구는 "레코드와 헤더 사이" 의 아주 짧은 구간만 다룬다.
- Phase 3 서버에서는 요청마다 INSERT 가 하나라 묶을 단위가 없다.

## 인덱스 대 선형 탐색 (S29)

### 방법

```bash
make bench                         # N = 1만, 10만, 100만 (약 1 분)
make bench BENCH_SIZES="10000"     # 규모 지정
```

- `bench/bench_index.c` 가 엔진 API (`engine_execute`) 를 직접 호출한다. 출력 비용은 들어가지 않고, 쿼리 텍스트 파싱·검증은 들어간다.
- 규모마다 `/tmp/minidb-bench-XXXXXX` 에 users 테이블을 새로 만들고, N 건을 SQL 로 넣은 뒤 엔진을 닫았다 다시 연다 (재구축 측정).
- 나이 (1 ~ 99) 와 무작위 키는 시드 고정 xorshift32 라서 실행마다 같다.
- **검증**: 측정하는 쿼리마다 결과 행 수와 `used_index` 가 기대값과 다르면 바로 실패 (종료 코드 1) 로 끝낸다. 범위 쿼리의 기대값은 넣을 때 센 `age >= 99` 개수로 계산한다.
- **콜드 / 웜**: 콜드는 `fdatasync` + `posix_fadvise(DONTNEED)` 로 테이블 파일의 페이지 캐시를 비운 직후 첫 실행. 웜은 이어서 반복한 평균 (인덱스 1,000 회, 선형 100 회).
- **무작위 k**: 같은 키 1,000 개를 두 경로에 번갈아 실행한 평균 (웜).
- 같은 조건으로 두 번 돌렸고 수치는 거의 같았다 (아래는 두 번째 실행). 첫 실행에서 10 만 건 INSERT 만 19 만 건/s 로 튀었는데, 다시 재니 30 만 건/s 였다.

## 해석

**O(log N) 대 O(N).** 인덱스 검색은 루트에서 리프까지 노드 3~4 개를 이진 탐색으로 지나고 레코드 1 개 (40 B) 를 `pread` 한다. N 이 100 배가 되어도 높이가 1 늘 뿐이라 약 2 µs 로 일정하다. 선형 탐색은 40 MB 를 256 건씩 읽으며 모든 레코드의 이름을 비교하므로 시간이 N 에 정비례한다 (0.32 → 3.36 → 33.9 ms). 배율이 N 과 함께 커지는 이유다 (T29-02, T29-03).

**트리 높이.** `BTREE_ORDER` 128 이면 노드 하나가 자식 128 개까지 가진다. 다만 id 가 늘 증가해서 split 이 반반으로 일어나므로 리프는 64 키, 내부 노드는 65 자식 정도만 찬다. 그래서 1 만 건 (리프 157 개 > 루트 한계 128) 에서 이미 높이 3 이고, 높이 3 의 용량 (약 128 × 65 × 64 ≈ 53 만) 을 넘는 100 만 건에서 4 가 된다.

**무작위 k 가 단건 반복보다 느린 이유.** 같은 k 를 반복하면 그 경로의 노드와 레코드 페이지가 CPU 캐시에 남는다 (2 µs). 무작위 k 는 매번 다른 리프를 지나고, 사이사이 선형 탐색이 40 MB 를 훑으며 CPU 캐시를 밀어내므로 캐시 미스가 섞인다 (3.4 → 9.3 µs). 그래도 N 100 배에 약 3 배로, 선형의 100 배와는 다른 증가다.

**k = 1 에서도 선형 탐색이 빠르지 않은 이유 (E29-02).** `name` 에는 유일성 제약도 인덱스도 없다. 첫 행에서 'user1' 을 찾아도 뒤에 같은 이름이 또 있을 수 있으므로 끝까지 봐야 한다 (k = 1, 50 만, 100 만 모두 약 34 ms). 반대로 `LIMIT` 이 있으면 선형도 일찍 멈춘다: `age >= 99 LIMIT 100` 은 약 1 % 인 행 100 개를 모으면 끝나서 (평균 1 만 행 정도) 0.08 ms 다. 선형 범위 쿼리의 비용은 N 보다 조건의 선택도에 달려 있다.

**콜드 캐시 (E29-01).** 콜드 인덱스 검색 (0.13 ~ 0.19 ms) 은 레코드 페이지 하나를 다시 읽는 비용이고, 웜 (2 µs) 의 약 70 배다. 선형 탐색은 콜드와 웜의 차이가 작다 (첫 측정 57 ms 를 빼면 34 ms 로 같음). 이 환경에서 "콜드" 는 컨테이너 VM 안의 페이지 캐시만 비운 것이고, VM 디스크 이미지는 호스트 (macOS) 가 다시 캐시해 두기 때문에 실제 디스크까지 가지 않는다. 40 MB 순차 읽기는 메모리 복사 수준으로 끝나고, 선형 비용 대부분은 100 만 번의 비교다. 진짜 디스크 콜드 측정은 호스트 캐시까지 비울 수 있는 리눅스 머신에서 해야 한다. 가장 처음 측정 (k = 1, 57 ms) 은 결과 버퍼 할당과 TLB 등 프로세스 쪽 첫 실행 비용이 더해진 값이다.

**bind mount 경로에서 재지 않는 이유 (E29-03).** 저장소 폴더 (`/workspaces/...`) 는 호스트 macOS 폴더를 Docker Desktop 의 파일 공유로 연결한 것이다. 그 경로의 쓰기는 VM 경계를 넘어 호스트 파일 시스템까지 간다. 같은 40 B `pwrite` 10 만 번을 재 보면 `/tmp` 는 호출당 0.8 µs, bind mount 경로 (`/workspaces/.../build/`) 는 81 µs 로 **약 100 배** 느렸다 (`pread` 는 캐시에서 읽혀 둘 다 0.6 µs). 100 만 건 INSERT 라면 쓰기만 2 분 40 초가 더 든다. 그러면 B+ 트리나 탐색 방식이 아니라 파일 공유 계층을 재게 된다. 그래서 벤치마크는 데이터를 항상 컨테이너 안 `/tmp` 에 만든다 (S28 의 삽입 측정도 마찬가지).

## 고정 오프셋이면 계산으로 찾을 수 있는데 왜 인덱스인가

지금 테이블은 id 가 1 부터 빈틈없이 이어지므로 `offset = 1024 + (id - 1) × 40` 으로 바로 계산할 수 있다. 그래도 인덱스를 만든 이유:

1. **범위 검색과 순서.** `id >= a` 는 시작점을 찾은 뒤 리프 연결을 따라가면 끝난다. 계산식은 "이 id 가 있는가" 와 "다음 id 는 무엇인가" 를 답하지 못한다. 빈틈이 생기는 순간 계산은 틀리고 트리는 그대로 맞다.
2. **삭제와 compaction.** `DELETE` 가 들어오면 빈자리가 생기고, 파일을 압축 (compaction) 하면 레코드가 옮겨져 id 와 위치의 관계가 깨진다. 트리는 id → offset 을 따로 가지고 있어서 위치만 갱신하면 된다.
3. **id 외의 키.** `name`, `age` 처럼 값과 위치 사이에 공식이 없는 컬럼은 인덱스 말고는 선형 탐색뿐이다. 같은 B+ 트리 구조를 키 타입만 바꿔 쓰면 된다 (위 표의 `name = 'userk'` 34 ms 를 µs 로 줄이는 방법).
4. **디스크 인덱스의 연습.** 실제 DBMS 의 인덱스는 노드가 디스크 페이지인 B+ 트리다. 차수, split, 리프 연결, 높이와 I/O 횟수의 관계를 메모리 버전에서 먼저 익히는 것이 목적이다. 이 프로젝트에서 트리 높이 4 는 "디스크였다면 페이지 4 번 읽기" 와 같다.

## Phase 3: HTTP 서버 부하 (S44)

### 방법

`bench/run_load.sh` (컨테이너 안에서 저장소 루트에서 실행) 가 아래를 자동으로 한다.

1. 두 락 방식으로 빌드한다: `make LOCK_MODE=GLOBAL`, `make LOCK_MODE=TABLE_RW`.
2. 10 만 건 원본 데이터를 한 번 만든다 (`tools/gen_sql.py 100000`). 측정할 때마다 복사해서 매번 같은 초기 상태로 시작한다.
3. `./minidb serve 18080 <워커> <큐>` 를 띄우고 `wrk -t4 -c64 -d30s -s bench/post_query.lua` 를 돌린다.
4. 끝나면 데이터를 검증하고 서버를 SIGINT 로 멈춘다.

**요청 (`bench/post_query.lua`)**
- 모든 값은 `params` 로 바인딩해서 보낸다.
- **id 읽기**: `SELECT * FROM users WHERE id = ?` (B+ 트리, 엔진 안 수 µs)
- **스캔 읽기**: `SELECT * FROM users WHERE name = ?` (10 만 건 선형 탐색, 엔진 안 수 ms)
- **쓰기**: `INSERT INTO users VALUES (?, ?)`

**처리량 측정의 큐 용량**
- 처리량을 잴 때는 큐 용량을 256 으로 둔다. 연결 64 개보다 커서 503 이 섞이지 않는다.
- 기본값 (워커 × 16) 이면 워커 2 개일 때 큐가 32 라서 요청의 절반 가까이가 503 이 된다.
- 503 응답은 금방 끝나므로 req/s 를 부풀린다. 그래서 표에는 200 을 받은 요청만 센 req/s 를 쓴다.

**데이터 검증 (T44-01)**
- `row_count` 증가분은 200 을 받은 INSERT 수에, 마감 순간 처리 중이던 INSERT (0 ~ 연결 수) 를 더한 값이어야 한다.
  - `wrk` 는 시간이 끝나면 응답을 기다리지 않고 연결을 끊는다.
  - 서버는 이미 받은 요청을 끝까지 실행한다. 그래서 그 INSERT 는 저장되지만 `wrk` 는 세지 못한다.
- 서버를 멈춘 뒤 CLI 로 다시 열었을 때 헤더 복구 경고가 없어야 한다. 테이블을 열 때 위치 k 의 레코드 id 가 k 인지 검사하므로, 경고 없이 열리면 id 가 중복·빈 곳 없이 이어지고 헤더와 파일이 맞는다는 뜻이다.

**늘어진 측정 걸러내기**
- 첫 전체 측정에서 두 건이 30 초 측정인데 `wrk` 가 잰 시간이 약 200 초로 늘어나 있었다.
  - 요청 수는 정상이었는데 req/s 가 터무니없이 낮게 나왔다 (742, 3.8).
  - 노트북 절전 등으로 Docker VM 이 잠깐 멈춘 것으로 보인다. 같은 경우를 따로 다시 재면 정상이었다.
- 그래서 스크립트가 `wrk` 가 잰 시간을 보고, 요청한 시간의 1.2 배를 넘으면 다시 잰다 (최대 3 번).
- 아래 결과는 다시 잰 경우가 없는 두 번째 전체 측정이다.

### 해석

**스레드 수별 처리량 (T44-02, E44-03): 늘지 않는다**
- id 조회 부하에서는 워커가 1 개든 16 개든 초당 약 1.5 만 ~ 1.9 만이다. 계획서가 기대한 "코어 수까지 증가" 는 나오지 않았다.
- 요청 하나에 드는 일 가운데 엔진 실행은 아주 작다.
  - id 조회는 약 2 µs, INSERT 는 약 3 µs 다 (Phase 2).
  - 나머지는 요청마다 하는 일이다. accept → 읽기 → HTTP·JSON 파싱 → 응답 JSON → `sendmsg` → lingering close.
  - 특히 TCP 연결 수립과 종료가 크다. 커널이 처리하고 `wrk` 쪽에서도 같은 비용이 든다.
- 코어 2 개를 `wrk` 와 서버 (워커, accept 스레드, 커널 네트워크 처리) 가 함께 쓰고 있어서, 워커를 늘려도 쓸 CPU 가 더 생기지 않는다. 워커 1 개도 이미 남는 CPU 를 거의 다 쓴다.
- 연결 받기는 accept 스레드 하나가 한다. 요청마다 연결을 새로 맺으므로 이 스레드도 상한이 된다.
- 코어 수보다 많은 워커 (8, 16) 에서도 처리량이 줄지 않았다. 워커 대부분이 큐 앞에서 잠들어 있어서 문맥 교환 비용이 드러나지 않는다.
- 워커가 많을수록 p50 이 조금 낮아진다 (3.05 → 1.70 ms). 큐에서 기다리는 요청을 꺼내 줄 워커가 늘어난 효과다.

**`GLOBAL` 대 `TABLE_RW` (T44-03): id 조회에서는 차이가 없고, 스캔에서 1.9 배**
- id 조회 90% 에서는 두 방식이 측정 오차 안이다. 오히려 `GLOBAL` 이 조금 높을 때가 많다.
  - 락을 잡는 시간 (수 µs) 이 요청 하나의 시간 (수십 µs 이상) 에 비해 너무 짧아서, 락을 기다리는 일이 거의 없다.
  - 그러면 남는 것은 락 연산 자체의 비용이다. `pthread_rwlock` 은 읽기 수를 세고 쓰기 대기를 관리하느라 `pthread_mutex` 보다 연산이 조금 무겁다.
- 락 안에 오래 머무는 선형 스캔 (10 만 건, 약 3 ms) 으로 바꾸면 차이가 바로 드러난다.
  - `GLOBAL` 은 스캔을 한 번에 하나씩만 해서 초당 251 이다. 1 / 251 ≈ 4 ms 로, 스캔 하나의 시간과 같다.
  - `TABLE_RW` 는 읽기 락끼리 동시에 들어가서 두 코어가 각자 스캔한다. 초당 477, 약 1.9 배다.
  - p50 도 243 → 131 ms 로 절반이 된다.
- 결론: RW 락의 이득은 "락 안에 있는 시간이 요청 시간에서 큰 비중을 차지하고, 읽기가 대부분일 때" 나타나며, 그 상한은 코어 수다.

**쓰기 100% (E44-02): 두 방식이 같은 이유**
- 테이블이 하나라서 `TABLE_RW` 에서도 INSERT 는 그 테이블의 쓰기 락을 혼자 잡는다. 전역 뮤텍스와 똑같이 한 줄로 선다.
- INSERT 하나의 락 구간도 수 µs (레코드 `pwrite` + 헤더 `pwrite` + `btree_insert`) 라서 여기서도 병목은 연결 처리다. 그래서 수치가 id 조회와 비슷하다.
- `GLOBAL` 21,351 대 `TABLE_RW` 17,761 의 차이는 측정 오차 범위와 락 연산 비용 수준이다.
- 테이블이 여러 개라면 `TABLE_RW` 는 다른 테이블끼리 동시에 쓸 수 있다 (`test_concurrency` 의 E40-04).

**과부하 (E44-01)**
- 연결 64 개, 워커 2 개, 큐 2 칸이면 요청의 78% 가 즉시 503 (`Retry-After: 1`) 을 받는다. 서버는 죽지 않고 끝까지 응답했다.
- 200 처리량 (4,203) 이 큐가 넉넉할 때 (약 1.7 만) 보다 낮은 이유는 두 가지다.
  - accept 스레드가 503 을 쓰고 닫는 데 시간을 쓴다.
  - 큐가 비는 순간이 생겨 워커가 쉰다.
- 백프레셔가 동작한다는 뜻이고, 큐 용량은 "연결 수보다 크게" 잡는 것이 좋다는 근거다.

**처리량을 더 올리려면**
- 이 측정에서 엔진은 병목이 아니었다. 다음 단계는 네트워크 쪽이다.
  - HTTP keep-alive (연결 재사용)
  - accept 를 여러 스레드로 (`SO_REUSEPORT`)
