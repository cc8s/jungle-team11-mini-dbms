# 벤치마크: 100만 건, 인덱스 켬 / 끔

```bash
make bench                 # 100만 건 (기본), wrk 10초
make bench ROWS=20000      # 작게
```

`tools/gen_data` 가 INSERT 문을 만들고(고정 시드), `bench/run_bench.sh` 가 적재 → 재시작 → 질의 → HTTP 부하 순서로 잰다. 인덱스 끔은 CLI·서버의 `-n` 옵션이다(같은 파일, 같은 질의, 탐색 방법만 다름).

## 결과 (2026-11-18)

- 행 수 1,000,000 · 22코어 · WSL2 (Linux 6.18) · gcc 15.2 `-O2`
- 행 크기 112바이트(`id INT, name VARCHAR(32), email VARCHAR(64), age INT`) → 파일 107MB

### 1. 적재와 재시작

| 항목 | 값 |
|---|---|
| INSERT 100만 개 (한 프로세스, SQL 파일) | **0.55초** (초당 약 180만 개) |
| 최대 메모리 (RSS) | 83MB (B+ 트리 포함) |
| 재시작 시 테이블 열기 = 파일 훑기 + B+ 트리 재구성 (3회) | **63~68ms** |

| 질의 | 인덱스 | 탐색 방법 | 확인한 행 | 중앙값 | 평균 |
|---|---|---|---|---|---|

## 읽는 법

- **id 검색은 약 7,900배**(0.002ms vs 15.8ms). 트리 높이가 3이라 노드 3개를 내려가고 행 하나를 읽는다. 선형 탐색은 107MB 를 다 읽는다.
- **HTTP 로는 약 400배**(46,217 vs 115). 차이가 줄어든 것은 요청마다 연결을 새로 맺고 JSON 을 만드는 고정 비용이 붙기 때문이다(keep-alive 없음, D006).
- 선형 탐색 HTTP 가 115 요청/초에 머무는 이유: 요청 하나가 107MB 를 `pread` 로 복사한다. 115 × 107MB ≈ 초당 12GB 로, 워커를 늘려도 메모리 대역폭에서 막힌다. SELECT 끼리는 읽기 락이라 동시에 돌지만(D005) 대역폭은 나눠 쓴다.
- `name =` 이 `id` 선형 탐색보다 2배 느린 것은 행마다 문자열을 꺼내 비교하기 때문이다.
- 재시작 63~68ms 는 107MB 를 읽으며 100만 개를 트리에 넣는 시간이다. append split 덕에 리프가 거의 꽉 차서(99.9%) 노드 수가 반이다(D003).

### 작은 테이블에서는 범위 검색이 선형 탐색보다 느렸다

2만 행으로 같은 벤치를 돌리면 `id BETWEEN a AND a+999` 가 **인덱스 켬 0.40ms, 끔 0.25ms** 로 뒤집힌다.

- 인덱스 경로는 행마다 `pread` 한 번 → 1,000행이면 시스템 호출 1,000번.
- 선형 탐색은 1,024행씩 묶어 읽는다 → 2만 행이면 20번.

100만 행에서는 선형 탐색이 1,000번 가까이 읽어야 해서 인덱스가 다시 43배 앞선다. 개선 방법은 분명하다: id 는 자동 증가이고 파일은 끝에만 붙으므로 **id 가 이어진 행은 파일에서도 붙어 있다.** 트리에서 받은 오프셋이 연속이면 한 번에 읽으면 된다. 지금은 손대지 않고 한계로 남긴다.
